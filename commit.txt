Two more cuts to gpu_sixteen3_tensor_kernel, checked separately rather
than bundled and assumed both mattered. Switched the six per-element
device buffers from alloc_zeros to alloc: every element gets written by
its own thread before anything reads it, so zeroing first is waste --
measured it alone first, and at n=10^9 it landed inside run-to-run noise
(176ms vs 180ms), not the win it looked like on paper. Shrunk the
regenerated x/y/z buffers from length n to length k=10,000, the actual
number the control check ever reads back -- writing all n of them was
3*n bytes of global memory traffic to feed a 3*k-byte reader. That one
was real: three repeated n=10^9 runs after landed at 101-119ms, cleanly
separated from the prior stage's 156-185ms range, not overlapping.

Kept both intermediate CSVs rather than overwrite them --
gpu_sixteen3_tensor_kernel_scaling_gpu_verify_gpu_rng.csv is what stage 3
(GPU verify, GPU RNG, full-n buffers) measured. Reran the full 10^4-10^9
sweep for stage 4: 110ms total at n=10^9, cumulative speedup over the
original CPU-verify version now 276x, up from 169x. Every stage still
checked on-GPU against the independent flat kernel and the CPU control
sample: 0 mismatches at every n tried, self-reference check holds.
