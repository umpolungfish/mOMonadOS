Recover sk_forge from the session log after an agent overwrote it

An agent building the BIP39 augmentation called chunked_write with mode='w'
twice. The first destroyed the 490-line file and rebuilt it by appending, which
worked and left 666 lines. The second, meant to replace sk_forge_main alone,
destroyed those 666 and left 211 — everything above the REPL surface gone: the
imports, SkForge, PublicKey, SecretKeyResult, Bip39PublicKey, the wordlist
loader. The tree stopped compiling on names that no longer existed.

Nothing in git had it. HEAD is 489 lines, the largest version ever committed is
544, no commit in any repo contains Bip39PublicKey, and the ig-docs copy is the
same 489. The work had never been committed, because the agent had only just
written it.

It was in the session log. tool_calls_json holds the arguments of every call, so
the three writes that BUILT the file — 4248 chars mode='w', then 20986 and 1679
appended — reconstruct it exactly: 26913 chars, 666 lines, matching what the
agent read back before destroying it.

Spliced the agent's own sk_forge_main over the stub it replaced, since that part
was an improvement: real subcommand dispatch where the file had returned an empty
string, which is why `sk_forge forge` printed nothing at all. Fixed two defects
the reconstruction carries because they were in the original — `}fn
format_result` run together, and a parse error formatted with {} on a tuple that
implements only Debug.

`sk_forge carriers` and `sk_forge forge` both answer now.

The lesson is about the tool, not the agent: a write mode that replaces a whole
file is indistinguishable, at the call site, from one that replaces a function,
and the agent's own verification — "wrote 4043 chars, file total 4159 bytes" —
reported success for an operation that had just deleted 23 kilobytes.
